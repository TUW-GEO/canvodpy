canvod.utils API reference¶

Shared date/time utilities and processing diagnostics. Configuration management lives in canvod.config instead.

Tools¶

Utility tools for canVODpy packages.

This module provides common utilities used across all canVODpy packages: - Version management - Date/time utilities for GNSS data - Validation helpers - File hashing - Deprecation warnings

Examples:

>>> from canvod.utils.tools import get_version_from_pyproject
>>> version = get_version_from_pyproject()

>>> from canvod.utils.tools import YYYYDOY
>>> date = YYYYDOY.from_str("2025024")
>>> print(date.to_datetime())

>>> from canvod.utils.tools import gpsweekday
>>> week, day = gpsweekday("15-01-2025")  # dd-mm-yyyy

>>> from canvod.utils.tools import isfloat
>>> isfloat("3.14")  # True

>>> from canvod.utils.tools import sanitize_directory
>>> sanitize_directory(store_path)  # removes stray .DS_Store files

>>> from canvod.utils.tools import deprecated
>>> @deprecated("Use new_function instead.")
... def old_function(): ...

YYYYDOY ¶

Year and day-of-year (DOY) date representation.

Used throughout canvodpy for GNSS data organization and file naming.

Notes

This is a Pydantic dataclass and uses total_ordering for comparisons.

Attributes:

Name Type Description
year int

The year (e.g., 2025).
doy int

Day of year (1-366).
date date

Calculated calendar date.
yydoy str

Short format (YYDDD, e.g., "25001").

Examples:

>>> # From components
>>> d = YYYYDOY(year=2025, doy=1)
>>> d.to_str()
'2025001'

>>> # From date object
>>> import datetime
>>> d = YYYYDOY.from_date(datetime.date(2025, 1, 1))

>>> # From string
>>> d = YYYYDOY.from_str("2025001")
>>> d.year

>>> # From short string (YYDDD)
>>> d = YYYYDOY.from_yydoy_str("25001")
>>> d.to_str()
'2025001'

get_version_from_pyproject(pyproject_path=None) ¶

Get the installed canvod-utils package version.

Tries importlib.metadata first, which resolves correctly for any install type (wheel, sdist, or editable). Falls back to walking up from this file's location looking for a pyproject.toml -- this only ever succeeds inside an editable/dev source checkout, since a built wheel's site-packages never ships pyproject.toml. Without the importlib.metadata path first, every store write from a non-editable install (a real PyPI release, or a git-sourced install like the demo notebooks use) raised FileNotFoundError here, since callers pass no explicit pyproject_path and expect this to just work.

Parameters:

Name Type Description Default
pyproject_path Path

Path to pyproject.toml. If None, resolved automatically as described above.

 None

Returns:

Type Description
str

Version string.

Examples:

>>> version = get_version_from_pyproject()
>>> print(version)  # e.g., "0.1.0"

Files from a GitHub link¶

Files read from a raw file link in a GitHub repository.

A file is named by its raw file link, at a commit, a tag or a branch::

https://raw.githubusercontent.com/<account>/<repo>/<commit>/<path>
https://raw.githubusercontent.com/<account>/<repo>/refs/tags/<tag>/<path>
https://raw.githubusercontent.com/<account>/<repo>/refs/heads/<branch>/<path>

The user is responsible for what the link points to. Each run fetches the file again; there is no cache. A run fetches a link once, into a folder of the run (:func:run_folder) that only its owner can read; the run's worker processes read the same file, so every part of a run sees the same content. A run folder is removed when the next run of the same process starts (:func:new_run), or when the process ends (the command, the notebook kernel, the Airflow worker). A run is one site; start the next one when the earlier one is done, since its fetched files are gone then.

A file in a private repository needs a GitHub token in the environment variable GH_TOKEN or GITHUB_TOKEN. canvodpy stores no secrets (ADR "Credentials come from the environment"). The token is only sent to raw.githubusercontent.com, never to the target of a redirect, and never appears in messages or logs.

A link is shown in the terminal (canvodpy doctor, error messages) but never recorded: stores and the run history get only its file name (:func:recorded_name, :func:without_urls). A process that runs more than once starts each run with :func:new_run.

canvod-filemap reads naming recipes with this module; canvodpy reads a settings file given as a URL with it.

run_folder() ¶

The folder of this run's fetched files, created if missing.

A new folder in the system's temporary folder that only its owner can read, removed when the process that made it ends. Worker processes started after it was made use the same folder (it is named in the environment variable CANVODPY_RUN_FOLDER), so they read the files the run fetched and leave its removal to the run.

The folder.

Logging¶

The run identifier and the stage timing; the log output is configured by canvodpy.setup_logging (see Diagnostics).

Logging helpers shared by the canvod packages.

The packages log through structlog: every module gets its logger with structlog.get_logger(__name__). The output (console, log files) is configured by canvodpy.logging.configure_logging; a package used without canvodpy logs through structlog's defaults.

  • :mod:~canvod.utils.logging.run_context: the run identifier added to every log record and Icechunk commit message of a run.
  • :mod:~canvod.utils.logging.stage_timer: timing of the processing stages and the end-of-run summary.

emit_run_summary(**context) ¶

Emit a run_summary event: per-stage breakdown for the current run.

The breakdown covers the stages timed in the main process (in canVODpy: writing the GNSS store, computing and writing VOD); the stages of the worker processes are only in the log. Called at the end of a successful run and also from the crash-handling path in cli/run.py, so a partial summary exists even for a run that later failed -- showing how far it got before dying.
