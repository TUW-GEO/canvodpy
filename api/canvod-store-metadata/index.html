canvod.store_metadata API reference¶

Rich provenance metadata for Icechunk stores, aligned with DataCite 4.5, ACDD 1.3, and STAC 1.1.

Package¶

canvod-store-metadata: store-level provenance for Icechunk stores.

This package manages store metadata: identity, creator, environment, software provenance, and standards compliance (DataCite/ACDD/STAC).

Not to be confused with the file registry in canvod.store ({group}/metadata/table), which tracks individual ingested files.

Bases: StoreLocation

A store in a directory on a local file system.

needs_commit_lock property ¶

Yes: Icechunk on a local file system can lose one of two concurrent commits without an error.

S3StoreLocation dataclass ¶

Bases: StoreLocation

A store under a prefix in an S3 bucket.

Credentials come only from the environment (the AWS_* variables, AWS_PROFILE) or the shared AWS files (~/.aws/credentials, ~/.aws/config), as do region and endpoint (AWS_REGION, AWS_ENDPOINT_URL): never from the settings or the store metadata, and they are never logged. CANVOD_S3_PATH_STYLE=1 puts the bucket in the request path, for S3 services that expect it.

needs_commit_lock property ¶

No: Icechunk's conditional writes on S3 keep two commits from overwriting each other, and there is no local directory to hold a lock file.

storage() ¶

The Icechunk storage, configured from the environment.

Raises:

Type Description
ValueError

If CANVOD_S3_PATH_STYLE is set to something other than yes or no.

__truediv__(relative) ¶

The location relative below this one, .. resolved.

S3 keys are plain names: S3 itself doesn't resolve .., so a catalog item's relative href is resolved here.

Raises:

Type Description
ValueError

If relative is an absolute path, or leads to the bucket's root or out of the bucket.

Raises:

write_metadata(store_path, metadata, branch='main') ¶

Write a new store's metadata.

The repository metadata (fixed and amendable fields, ADR 0014) is written once; a first commit writes its root copy and the snapshot summary, with metadata.config as the settings in the commit metadata.

Returns:

Type Description
str

Snapshot ID from the commit.

Raises:

Type Description
StoreCreatedByAnotherRunError

If the store already has repository metadata, or another run committed its creation first. A store on S3 has no commit lock, so two runs may both find it without metadata; the creation commit does not rebase, so only one of them creates it (#358).
ValueError

If metadata lacks a fixed field (build it with collect_metadata), or a field breaks a rule of its standard (e.g. a license outside SPDX).

open_repository(location, *, create=False, config=None, expected_uuid=None) ¶

Open the repository of the store at location.

Opening never creates a repository, and creating never opens one, so a mistyped location fails instead of leaving an empty store behind.

Parameters:

Name Type Description Default

Create a new repository instead of opening one.

 False
config RepositoryConfig | None

The repository configuration (compression, caching, concurrency). None creates a store with the defaults of the processing.icechunk settings (:func:repository_config), so it matches a store a run creates, and opens one with the configuration Icechunk kept with the store.

 None
expected_uuid str | None

The UUID of the store the caller expects, for example from a catalog item. A store with another UUID, or without repository metadata, is refused, so a store replaced behind the same location is never taken for the old one.

FileExistsError

ValueError

Collectors¶

Runtime collectors: pure functions that gather metadata.

collect_software_versions() ¶

Collect versions of key packages via importlib.metadata.

collect_python_info() cached ¶

Return the Python version number and implementation ("3.14.8 CPython").

Not sys.version: it adds the build date and the compiler, and the store records no machine information.

collect_uv_version() cached ¶

Return the uv version number, or None if uv is not installed.

Only the number is kept ("0.13.1"): uv --version may add how uv was built and the platform, for example "uv 0.13.1 (Homebrew 2026-10-14 aarch64-apple-darwin)", and the store records no machine information. Asked once per process.

collect_environment(store_path=None, dask_workers=None, dask_threads_per_worker=None, record_machine=True) ¶

Collect runtime environment information.

With record_machine=False the computer (operating system, architecture, CPU count, memory, free disk) is not recorded: those fields are None (processing.metadata.record_machine).

records_machine(config) ¶

processing.metadata.record_machine of config: settings, a plain dict of them or a :class:ConfigSnapshot; true when not set.

collect_config_snapshot(config) ¶

Serialize config sections + compute SHA256 hash.

Left out (and out of the hash), because stores are shared: processing.credentials, the account details for data servers, and the settings of one computer (:data:~.machine.MACHINE_SETTINGS, and the stores' root when it is a local folder). The same settings on two computers give the same hash.

Build Creator from MetadataConfig.

collect_publisher(metadata_config) ¶

collect_spatial(site_config, site_name) ¶

Build SpatialExtent from SiteConfig.

collect_receiver(receiver_config, site_name=None) ¶

A receiver's entry in the store metadata, from its settings.

With site_name, a receiver with a naming recipe also gets the sha256 of its recipe file (:func:recipe_sha256_of). A recipe given as a URL is recorded by its file name only.

recipe_sha256_of(site_name, recipe) ¶

sha256 of the naming recipe file recipe of site_name.

The file is found the way a run finds it (canvod-filemap's find_recipe: a local recipe in the configuration directory, or a URL recipe, fetched).

Returns:

Type Description
str | None

The hexadecimal sha256, None if canvod-filemap is not installed or the recipe cannot be found (a run stops there before any store is written).

collect_instruments(site_config, *, hardware=True, site_name=None) ¶

Build Instruments from SiteConfig receivers.

hardware=False leaves out the receiver and antenna details: a VOD store reads them from the GNSS store's entries instead of copying them.

collect_vod_analyses(site_config) ¶

The VOD analyses of a site, for its VOD store.

collect_processing_provenance(store_type, source_format, facility=None) ¶

Build ProcessingProvenance.

facility is the institution that processed the data (processing.metadata.institution), never the computer.

collect_references(config) ¶

Build References from config if available.

missing_store_settings(site_name, site_config, config) ¶

Return the settings a new store needs but does not have.

A store records these when it is created (DataCite, STAC): the site's store description, the publisher, the license and the naming authority. Each returned name carries an example value, as the store-creation error lists them. The deprecated shared processing.metadata.store_description still counts as the site's store description.

The naming authority is checked with check_naming_authority: it is listed as missing when it is absent or not a reverse DNS name.

commit_lock(store_path) ¶

Let only one commit at a time change the store at store_path.

Icechunk on a local file system is not safe for concurrent commits: when two commits run at the same time, both can return successfully while one of them is lost. This lock, a file in the store directory, makes every other commit wait, in this process (other threads) and in other processes on the same machine. A commit that waits then sees the commit before it, and :func:commit_with_rebase rebases onto it.

The lock is re-entrant in one thread. The operating system releases it when the process that holds it ends.

commit_with_rebase(session, message, metadata=None, *, store_path, config=None, repository=None, rebase=True, keep_summary=False) ¶

Commit a session, rebasing it if the branch moved since it was opened.

The commit holds :func:commit_lock for store_path, the store the session belongs to, so commits to one store run one after the other. Several writers may still work on one store at the same time (e.g. two receivers of a site): when the branch moved since a session was opened, icechunk.ConflictDetector rebases changes that do not overlap (e.g. different groups) onto the new tip; overlapping changes fail with icechunk.RebaseFailedError.

A commit of data checks the run's content settings against the store's at the tip, after the rebase (ADR 0019): another run may have created the store or written first. A commit that changes the repository metadata (creation, amendment, migration) is not checked.

The commit also writes the root copy and the snapshot summary of the rebased session (ADR 0014); the summary is updated from the log-book rows added since this process's last commit to the branch, and rebuilt from the whole store at its first (ADR 0021, :mod:~canvod.store_metadata.summary_state). It records software, environment and settings as commit metadata, next to metadata. The lockfile text is stored once per hash: before a commit of data, in a commit of its own when the branch does not hold it yet (:func:store_lockfile), so two runs' data commits don't both write it and conflict (#352); a commit that changes the repository metadata carries it itself.

It refuses a store without repository metadata, so no store holds data without it, and a root group that differs from the repository metadata.

Every commit in canVODpy goes through this function, except manifest compaction, which goes through :func:rewrite_manifests.

config Any

 None

The repository metadata the commit carries, when it is about to change (creation, amendment, migration): the caller writes it with Repository.set_metadata only after the commit succeeded, so a failed commit leaves the repository metadata as it was. None uses the store's current repository metadata.

False commits only onto the snapshot the session was opened on: if the branch moved, the commit fails with icechunk.ConflictError instead of rebasing. The creation of a store uses it, so of two runs that create one store at the same time only one commit lands (:func:write_metadata).

Catalog¶

The STAC catalog of all stores under a data root (ADR 0015).

A static catalog beside the stores, never inside one: catalog.json, one collection per product (gnss-observations, vod, gnss-geodesy) and one item per store, all links relative, so the data root can be copied or moved. The catalog is derived from the stores and is written only on request.

Each asset names what opening its dataset needs: the store (href), the group (xarray:open_kwargs) and the snapshot (canvod:snapshot_id).

The catalog never leaves a store out silently: every store under the root is read first, and if any cannot be described, one error lists them all and nothing is written.

Each write replaces the latest catalog fully: the catalog, collection and item files of the previous write that the new one has no use for are removed, and only those. Any other file stays, and releases/ is never touched. Each file is replaced in one step, so a reader or a second writer never sees half a file; of two writers at once, the last one wins.

A release (:func:create_release) tags main in every store with the same Icechunk tag and writes the catalog of that tag under releases/<tag>/: the same tree, each asset pinned to the tag and the snapshot it points at. A release catalog is never changed afterwards.
