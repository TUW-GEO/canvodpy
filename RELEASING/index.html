Release process¶

Maintainers only

This guide is for repository maintainers with push access to the main branch.

Prerequisites¶

Before starting a release:

  • All CI checks passing on main
  • main branch is stable
  • All changes committed and pushed
  • You are a maintainer: main requires a PR (step 4), and only maintainers can create release tags (step 5)
  • The release files (pyproject.toml files, uv.lock, the CHANGELOG.md files, CITATION.cff, .zenodo.json, codemeta.json) have no uncommitted changes; just release refuses otherwise. Other changes in the working tree stay out of the release commit.

Release types¶

Each package has its own version (Versioning); choose the increment of each package you release:

Type Version Bump Example When to use
Patch 1.1.X 1.1.0 \(\rightarrow\) 1.1.1 Bug fixes only, fully backwards compatible
Minor 1.X.0 1.1.0 \(\rightarrow\) 1.2.0 New features, backwards compatible
Major X.0.0 1.4.0 \(\rightarrow\) 2.0.0 Breaking changes; requires an upgrade guide (Upgrading to v1.0.0 is the one for v1.0.0), linked from the README, the docs landing page, the changelog, and the release notes

canvodpy is part of every release, and its increment is at least the largest of the packages released with it.

To test a release first, publish it as a pre-release (1.0.0a1, 1.0.0b1, 1.0.0rc1); Versioning explains the stages and when to choose which. The steps below are the same.

The Development Status classifier in every pyproject.toml follows the release: 4 - Beta for a pre-release, 5 - Production/Stable for a stable release. The first stable release (1.0.0) changes it from 4 - Beta to 5 - Production/Stable in all packages, in a pull request before step 1; PyPI shows the classifier of each release.

Step-by-step¶

1. Prepare¶

git checkout main
git pull origin main
just test && just check

2. Choose the packages and versions¶

just release-status

For each package: its version, its last release tag, and the commits since that tag that touched the package's folder. Release a package when its commits matter to its users, at the increment they call for.

3. Create the release¶

just release canvod-store=1.1.0 canvod-grids=1.0.1 canvodpy=1.1.0

This command:

  1. Runs all tests (just test)
  2. Refuses the release, and says why, when canvodpy is missing, a version does not go up or is tagged already, canvodpy's increment is smaller than a package's, a package's range on another excludes the new version (or the current version of a package left out of the release), a citation file lacks its version or date field, a release file has uncommitted changes, or the branch release/v1.1.0 exists already (locally, or on the remote as of your last git fetch)
  3. Writes the new versions, canvodpy's == pins, a section in each released package's CHANGELOG.md (from the commits that touched its folder; canvodpy's lists the pinned versions), canvodpy's version and today's date in CITATION.cff, .zenodo.json and codemeta.json (Zenodo takes the version of the archived record from them), and uv.lock
  4. Creates the branch release/v1.1.0 (canvodpy's version) and commits exactly the release files: bump: canvodpy 1.1.0 (canvod-store 1.1.0, canvod-grids 1.0.1)

It creates no tag: the tags belong on the merged commit on main (step 6).

4. Review¶

git show --stat     # the version files, uv.lock and CHANGELOG.md files, nothing else

The changelog sections are generated from commit subjects; edit them in the release branch if a line needs it.

5. Open a PR for the release commit¶

main requires a PR. Push the branch and open one:

git push -u origin release/v1.1.0
gh pr create --title "bump: canvodpy 1.1.0 (canvod-store 1.1.0, canvod-grids 1.0.1)" --body "..."

Merge the PR once CI passes.

6. Tag the merged commit¶

A merge can give the release a different commit than the one on the branch, so the tags are created only now, on main:

git switch main
git pull origin main
just tag-release
git push origin v1.1.0 canvod-store-v1.1.0 canvod-grids-v1.0.1

just tag-release creates an annotated tag for every package version that has no tag yet, and prints the push command; it does not push.

7. Publish the draft release¶

The .github/workflows/release.yml workflow detects the canvodpy tag (v1.1.0) and creates a draft release whose notes are canvodpy's CHANGELOG.md section, including the package versions. Package tags get no GitHub release of their own. Review and publish at github.com/TUW-GEO/canvodpy/releases.

Pushing the tags does not publish to PyPI: tagging and PyPI publishing are deliberately decoupled (see step 8).

8. Publish to PyPI (separate, manual, whenever you decide)¶

Not automatic. Trigger publish_pypi.yml on the canvodpy tag, either from the Actions tab (the Run workflow button; choose the tag) or:

gh workflow run publish_pypi.yml --ref v1.1.0

It first checks the locked dependencies against known vulnerabilities (just audit) and stops if it finds one. Then it builds and uploads exactly the packages whose release tag points at that commit (scripts/release.py tagged), here canvodpy, canvod-store and canvod-grids. You can create several releases before ever running this: a tag existing is not a promise that PyPI has it.

9. Post-release¶

  • Monitor issues for regressions
  • Check the Zenodo record the release created: its version must be canvodpy's (Zenodo Setup)

Troubleshooting¶

Tests fail during release

Fix the failing tests on main before retrying just release.

Not released

just release names every problem it found; nothing was changed. Typical ones:

  • canvodpy pins every package: add canvodpy=X.Y.Z.
  • canvod-store makes a minor release, canvodpy only a patch: raise canvodpy's version.
  • canvod-grids requires canvod-store<2,>=1.0.0, which excludes canvod-store 2.0.0: check canvod-grids against the new major version, widen its range in its own pull request, then release both.
  • canvod-store requires canvod-utils<2,>=1.0.0, which excludes the current canvod-utils 0.4.0: canvod-utils is left out of the release, but the new canvod-store needs a newer one. Add canvod-utils=X.Y.Z.
  • Release files have uncommitted changes: commit them in their own pull request, or discard them.
  • The branch release/v1.1.0 exists already: a branch of that name is left from earlier work (for v1.0.0, the integration branch release/v1.0.0). Delete it once it is merged, locally and on GitHub, then run just release again.
Version is not a version

Use NAME=X.Y.Z with an explicit version (no v prefix): 

just release canvodpy=1.1.0    # correct
just release canvodpy=v1.1.0   # wrong

Tag already exists

A pushed release tag is not moved: release the next patch version instead. A tag that exists only locally can be deleted with git tag -d v1.1.0.

Draft release did not appear

Verify the canvodpy tag matches the pattern v*.*.* at github.com/TUW-GEO/canvodpy/actions, and that CHANGELOG.md has a section ## v1.1.0 (...). (PyPI publishing never triggers from a tag push at all; see step 8.)

Tag is not allowed to deploy due to environment protection rules

The pypi environment accepts only tags of the form v*.*.*, the canvodpy tags. Run publish_pypi.yml on the canvodpy tag, never on a package tag such as canvod-store-v1.1.0: it publishes every package tagged on that commit.

The dependency check finds a vulnerability

just audit names the package, the vulnerability and the version that fixes it. Raise the version in uv.lock (uv lock --upgrade-package NAME) in a pull request, and tag the release on the new commit. If no fixed version exists and the vulnerability doesn't affect canVODpy, add --ignore-vuln ID to the just audit call of both workflows, with a comment saying why, and remove it once a fix is out.

A new package fails its first upload

A package that is not on PyPI yet needs a pending publisher on PyPI (the repository, publish_pypi.yml and the pypi environment). PyPI allows only one pending publisher per repository, workflow and environment, so two new packages need two runs: add the first package's pending publisher and run the workflow, then the second's and run it again. Files already on PyPI are skipped (uv publish --check-url).
