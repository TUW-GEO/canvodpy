canvod-store¶

canvod-store keeps the data of a site in two Icechunk stores: the GNSS store holds the observations of every receiver, and the VOD store holds the VOD results. Icechunk stores Zarr arrays and records every write as a commit, so earlier states of a store stay readable.

This page describes what the stores hold, how a run writes to them, and how to read them in your own code.

The two stores of a site¶

Each site has its own GNSS store and VOD store, both under processing.storage.stores_root_dir:

<stores_root_dir>/
└── ExampleSite/
    ├── gnss/    # GNSS store (processing.storage.gnss_store_name)
    └── vod/     # VOD store (processing.storage.vod_store_name)

The GNSS store holds data from every reader format (RINEX, SBF, and NMEA).

Store folders¶

A store's folder is named by its kind: gnss, vod, or geodesy. For a second store of the same kind at a site, for example to compute VOD again with other settings, the name is the kind, - and a suffix of lowercase letters and digits, with single _ or - between them: vod-recompute, gnss-test. Any other name is refused when the settings load. The store id is the site name and the folder, examplesite-vod-recompute; it is fixed when the store is created, so a store's folder can't be renamed later (a run refuses it, naming the cause).

Before v1.0.0 the GNSS store's folder was rinex. canvodpy store migrate SITE moves it to gnss (Upgrading to v1.0.0).

A store knows its site from its own metadata, not from the folder it sits in: store.site_name stays the same when the folder is moved or renamed. A store written before stores kept repository metadata has no site name; reading it raises an error that names canvodpy store migrate.

Groups¶

A store holds one group per receiver, or per VOD analysis.

In the GNSS store:

  • A canopy receiver has one group, named after the receiver, for example canopy_01.
  • A reference receiver has one group per canopy receiver it is paired with, named {reference}_{canopy}, for example reference_01_canopy_01.

In the VOD store, a group is named {calculator}/{analysis}, for example tau_omega/canopy_01_vs_reference_01.

The data variables of a GNSS store group (for example SNR, Phase, Pseudorange, and Doppler, depending on the reader) have the dimensions epoch and sid and sit directly in the group:

canopy_01/
├── SNR
├── Phase
├── ...
└── metadata/
    ├── table     # log book: one row per stored file
    └── sbf_obs   # SBF receivers only: receiver metadata per file

sbf_obs keeps the missing value each variable declares, as both the CF _FillValue and the Zarr fill_value: -1 for the integer flags (for example rise_set and pvt_mode), NaN for floating-point values.

The log book (metadata/table) records each stored file: its hash, start, end, filename, the dataset attributes, and the preprocessing record (see Preprocessing during a run). In a group made of day blocks, it also records how many epochs of the file were stored (epochs). Every other value in it is text, JSON, or a time.

The log book only grows: rows are appended, never changed. A run reads each group's log book whole the first time it needs it and afterwards only the rows committed since, by itself or by another run, so checking a day against it takes the same time however many days the store holds.

Day blocks¶

A new GNSS store is written as day blocks (ADR 0016). The epoch axis of a group holds one block per day, with one slot for every epoch of the day at the day's cadence: 17280 slots for a day at 5 s, 86400 at 1 s. Blocks are stored in the order the days were first processed; reading a group returns its epochs in time order.

A run adds the blocks of a unit of days in one small commit, after it has prepared the days and before it reads any file. Only days whose orbit and clock products are ready get a block; the cadence comes from the filenames, so the run reads no file for this. If the files of a day then fail, its block stays empty and the next run of that day uses it. A group's first write creates the group and its first blocks. If another run added blocks to the store in the meantime, the run reads the store again, uses the blocks already there, and adds the rest.

  • Each epoch of a file goes into its nearest slot: 00:00 of the day plus a multiple of the cadence. The epoch coordinate keeps the epoch's real time.
  • A slot without data holds its grid time in epoch, NaN in floating-point variables, and -1 in integer variables such as LLI and SSI (their _FillValue).
  • A write fills the slots from the file's first to its last epoch. When the log book already holds a file of the same canonical name, the write also empties the slots of that earlier write that the file now has no epochs for, but never slots inside another stored file's span. Writing a file again therefore never adds epochs, a file that now has fewer epochs leaves nothing of its earlier write, and a file written for the first time leaves the rest of its named period alone (after a receiver restart, the next file can start inside it). A file without a canonical name (possible with temporal_aggregation) replaces only the slots from its first to its last epoch.
  • The cadence of a day is the finest sampling interval in the names of the files of the day, or the bin length of processing.preprocessing.temporal_aggregation when it is set. Every cadence is stored, and days in one group can have different cadences. A day has ceil(86400 s / cadence) slots; its block holds whole chunks of 180 epochs (processing.icechunk.chunk_strategies.gnss_store.epoch), padded with empty epochs where the slots don't fill the last chunk (84 per day at 15 min, none at 1 s to 1 min). Padding epochs lie between the day's last slot and the next day, and loading leaves them out. A group keeps the chunk size it was created with: a changed setting applies to new groups only (see Chunks).
  • A group records its layout in its attributes (epoch_layout: day_blocks) and the block of each day in day_block_index (start and stop on the epoch axis, slots, cadence). A store whose groups were written by appending files to the epoch axis, by canVODpy versions before day blocks, is refused by runs until it is moved to day blocks (see Moving a store to day blocks).

GnssResearchSite.read_receiver_data() returns only the slots with data. MyIcechunkStore.read_group() returns every slot; with drop_empty=True it leaves out the empty ones (slots where every floating-point variable is missing).

The VOD store¶

A VOD store group is made of day blocks when the canopy or the reference group of its analysis is. A day of VOD gets the cadence of its GNSS data: the coarser of the two groups' cadences for that day, so every VOD epoch has its own slot. Slots without VOD hold NaN.

  • A run writes the VOD of each day with its own commit. The VOD of all analyses of a day shares that commit.
  • A write covers exactly one day; a result of more than one day is refused (LayoutError). The log-book row of a write records how many epochs of the day hold VOD (epochs).
  • A result computed from the same GNSS files as a stored one isn't written; the run logs it. A result from other GNSS files, for example after more files of the day were stored, is written into the day's slots and replaces the VOD that was there. Its log-book row records the action overwrite.
  • VOD is computed only from GNSS groups made of day blocks, and written only into VOD store groups made of day blocks. Either store written by appending is refused (LayoutError, naming the command that moves it).

GnssResearchSite.read_vod_analysis() leaves out the empty slots, as read_receiver_data() does; with drop_empty=False it returns every slot.

Moving a store to day blocks¶

A store written by canVODpy versions before day blocks holds groups written by appending files to the epoch axis. Runs write day blocks only, so they refuse such a store. Move it once:

canvodpy store migrate-layout SITE --store gnss
canvodpy store migrate-layout SITE --store vod

The command shows, for each group, its days, their cadences, its epochs and the duplicate entries it drops, and asks before it changes anything (--yes skips the question).

  • Each group written by appending is written again, day by day. Each day gets a block at its cadence: the finest step between its epochs, rounded to 1 ms. A day with a single epoch takes the finest cadence of the group. Days may have different cadences.
  • An epoch stored more than once, for example by unsafe_append, keeps the entry written last.
  • A group keeps its attributes, its log book and its other metadata (sbf_obs). It gets the chunks of the settings (processing.icechunk.chunk_strategies).
  • The log book gets the epochs column, so the snapshot summary counts each epoch once, for the latest write of its file.
  • Everything goes into one commit. Snapshots from before keep the old layout and stay readable.

A store written before repository metadata needs canvodpy store migrate-metadata first; migrate-layout refuses it and names that command.

How a run writes¶

canvodpy run writes to both stores; in your own code, read from them.

On a file system, Icechunk can't detect two commits at the same time: both can report success while Icechunk loses one of them (Icechunk: storage). So every commit to a store first takes the store's commit lock, the file .canvodpy-commit.lock in the store directory. A commit from another thread or process, for example a second run or a scheduler task, waits until the lock is free. Write a store from one computer only.

Two Icechunk warnings don't apply to these stores, so canVODpy hides them: that the file system is not safe for concurrent commits (the commit lock covers this), and that a lost reply to a write may show up as a conflict (Icechunk's file system storage makes one try per write and keeps no write metadata). Every other Icechunk warning is shown. To set your own filter, set the environment variable ICECHUNK_LOG, for example ICECHUNK_LOG=icechunk=debug.

For each receiver and day, a run does the following:

  1. Reads the files and computes the satellite angles.
  2. Applies the preprocessing in processing.preprocessing, if set.
  3. Checks each file against the group's log book (see Duplicate checks).
  4. Writes the new data with one commit: the worker processes write the files into their slots, and one commit writes the day of all receivers. The same commit writes the snapshot summary and records the commit metadata (see canvod-store-metadata).

A write must match the group. A run stops with an error if:

  • the data has other variables than the group (GroupVariablesMismatchError);
  • the data has other sid labels than the group (GroupCoordinatesMismatchError). The labels are stored once per group, so an append with other labels, for example after you change processing.params.aggregate_glonass_fdma, would relabel the stored data;
  • the epochs aren't in GPS time, or the group doesn't record its time scale (EpochTimeSystemError). Every stored epoch is GPS time (epoch.attrs["time_system"] == "GPS"). Groups written by canVODpy before it stored every epoch in GPS time have no record (their SBF and NMEA epochs were UTC, 18 s earlier); write to a new store;
  • a day stored at a coarser cadence gets a file sampled more often (CadenceError);
  • a file would be appended to a group made of day blocks, or the store holds groups written by appending (LayoutError).

A file with two epochs in one slot, for example because its name gives a coarser sampling than its data, isn't stored: the run logs a SlotCollisionError and writes no log-book row for the file, so the next run tries it again.

If another commit lands while a write is in progress, canVODpy rebases the write onto it when the two changed different groups. If both changed the same data, the later commit fails with icechunk.RebaseFailedError and writes nothing. The run then plans and writes the whole unit again on top of the other commit, up to five tries in all, with a growing wait in between. When the last try fails too, the run records the receivers and days as failed in its run history, with the error, and goes on with the next days. It does the same when it can't add the blocks of a unit.

Duplicate checks¶

Before a run writes a file, it checks the file against the group's log book, in three ways:

Check What it finds Where
Hash The same file, already stored (SHA-256 of the file) The orchestrator, and again just before the commit
Time span A file whose time span overlaps stored data, also when it has another name or other start and end times The orchestrator, and again just before the commit
Batch Two files of one batch that cover the same time The orchestrator

A file with the same hash counts as already stored: the default write strategy, skip, doesn't write it; overwrite replaces its time range. A file with another hash over stored data stops a run with skip, and replaces the stored data with overwrite; the run checks it again just before each commit. A file that overlaps another file of its batch is skipped. For details, see Write strategies.

Read a store¶

Open the stores of a configured site with Site:

from canvodpy import Site

site = Site("ExampleSite")
site.gnss_store.list_groups()  # ["canopy_01", "reference_01_canopy_01"]
site.gnss_store.get_group_info("canopy_01")

ds = site.gnss_store.read_group("canopy_01")
ds_day = site.gnss_store.read_group("canopy_01", date="2025001")
ds_range = site.gnss_store.read_group(
    "canopy_01", time_slice=slice("2025-01-01", "2025-01-15")
)

read_group() returns an xarray.Dataset that reads its data only when a value is needed, its epochs in time order. date="2025001" selects that day only: from 00:00 up to, not including, 00:00 of the next day. A time_slice includes both of its ends, and an end written as a date ("2025-01-15") means the whole of that day. For how reads load chunks, see Chunks; for earlier states of a store, see Versioning with Icechunk.

To open a store by its path, use open_gnss_store() or open_vod_store():

from canvod.store import open_gnss_store

store = open_gnss_store("/data/stores/ExampleSite/gnss")

Opening a store never creates one: a path without a store raises a FileNotFoundError that names the path. A run creates a site's stores when it first writes data, together with their metadata (see canvod-store-metadata). Site opens its stores only when you first use them, so a new site has no stores until a run writes to it. create_gnss_store() and create_vod_store() are left over from development: they open a store as well, and are removed with the next major version.

Reading a store needs no settings file, so a store you downloaded or got from a colleague opens as it is. Without a settings file the store opens with the configuration Icechunk keeps with it. Reads work, and so do branches and tags. Commits need the settings, because a commit records them, and so do expiring snapshots and garbage collection, a dry run included. On a store opened without settings they raise a FileNotFoundError that names canvodpy config init. Create the settings with it, then open the store again. A settings file that is there but can't be loaded fails the opening, as before.

Compare two stores¶

compare_stores() compares two stores and returns a report of every difference, per group and variable. It works on any two stores, for example the reference stores of the test data and the stores a change produces (spec #318), or a production store before and after an upgrade. It only reads, through MyIcechunkStore (list_data_groups and read_group), and never changes how a store is written or read.

Open each store by its path, then compare:

from canvod.store import compare_stores, open_gnss_store

reference = open_gnss_store("/data/stores/ExampleSite/gnss")
new = open_gnss_store("/data/stores/ExampleSite-new/gnss")
report = compare_stores(reference, new)

report.matches  # True when the stores are the same
print(report.to_text())  # a report for a person
report.model_dump_json()  # a report for CI

The comparison uses xarray.testing: assert_allclose within the tolerance below for the float variables of the table, and assert_identical for everything else (integer and flag variables, coordinates, other floats). The report lists a group present in one store and not the other, a lost epoch or a renamed SID, a changed value (also a value present in one store and missing in the other), with the count of differing values, the largest difference and xarray's message.

Attributes are compared too, those of the store, the groups and every variable, also nested ones (the report names the inner key, for example canvod:repository_metadata.identity.title). Left out are only the attributes that change with every run or release: the creation and modification times, the store ids, the canvodpy version and the Software attribute, and the content hash of the GNSS store a VOD store was computed from (its values are compared themselves). The list is VOLATILE_ATTRIBUTES in the same module. A changed input file therefore shows as a changed File Hash. A new or changed setting shows under canvod:repository_metadata.content_settings, by name and in its hash: it changes what the store records about how it was built, so it counts as a difference.

The log books (metadata/table) are not compared. They record how a run wrote each file (write times, snapshot ids, run ids, paths); what the files hold is compared through the groups, and which files were read through File Hash.

Float variables are compared within one absolute tolerance per variable, derived from the finest resolution any format records. A float variable not in the table is compared exactly and is reported as no_tolerance, so a new variable is noticed.

Variable Tolerance Derivation
SNR (also 1-minute means), Pseudorange, Phase, Doppler 5e-4 half the RINEX observation resolution, format F14.3 = 0.001 (RINEX 3.04, observation record, p. 67; RINEX 2.11, observation record). SBF (0.25 dB-Hz) and NMEA GSV (1 dB-Hz) are coarser.
delta_snr 1e-3 a difference of two SNR values, 2 × 5e-4
VOD 2e-4 VOD = -(ln 10 / 10) · delta_snr · cos(theta); (ln 10 / 10) × 1e-3 = 2.3e-4, rounded down
theta, phi 1e-6 rad above the float32 spacing at pi/2 (1.2e-7 rad), the precision the angles are stored with; a larger difference is a changed satellite geometry

The tolerances, with their derivation and sources, are one constant in the code: FLOAT_TOLERANCES in packages/canvod-store/src/canvod/store/comparison.py (spec #318).

The JSON form carries matches, so a CI check can read the result.

History¶

Each store keeps its commits and the operations on it:

store = site.gnss_store

store.print_history(limit=20)  # commits on main, newest first
store.plot_commit_graph()  # commit graph: SVG in a notebook, text in a terminal
store.print_ops_log(limit=30)  # commits, branch operations, expiry, garbage collection

store.create_release_tag("v1.0")  # tag the latest commit on main
store.list_tags()
store.compare_snapshots(snapshot_id_1, snapshot_id_2)

Command line¶

canvodpy store shows the stores of a configured site; store log --path also shows a store outside the settings:

canvodpy store list                                 # GNSS and VOD store paths of every site
canvodpy store info ExampleSite                     # branches, groups, and statistics
canvodpy store info ExampleSite --group canopy_01   # the dataset and log book of one group
canvodpy store log ExampleSite                      # commit graph
canvodpy store log ExampleSite --ops                # operations on the store
canvodpy store log --path /data/copy/gnss           # commit graph of a store outside the settings
canvodpy store log ExampleSite --svg history.svg    # commit graph as an SVG file
canvodpy store log ExampleSite --plain              # commit graph without colors, for files and CI logs
canvodpy store maintain ExampleSite                 # what expiry and garbage collection would delete
canvodpy store migrate-layout ExampleSite           # move a store written by appending to day blocks

--store vod opens the VOD store instead of the GNSS store, and --branch selects a branch other than main. For every option, see the command-line reference.

On a store on S3, maintenance is a dry run only: another machine may be writing to the store, so canvodpy store maintain reports what it would do and --execute is refused, and canvodpy store maintain-due reports a due store without changing it. See ADR 0019.

Grids and analysis results¶

store_grid() writes a hemispherical grid to the grids/{grid_name} group of a store, and load_grid() reads it back. A grid read back works for cell assignment only if it's an equal-area, equal-angle, or equirectangular grid; for the other grid types, build the grid again with create_hemigrid().

from canvod.grids import create_hemigrid
from canvod.store import load_grid, store_grid

grid = create_hemigrid("equal_area", angular_resolution=4.0)
store_grid(grid, store, "equal_area_4deg")
grid = load_grid(store, "equal_area_4deg")

AnalysisStorage stores the results of an analysis on a grid in a VOD store: weights, masks, statistics, and time series per cell. The time series per cell go to the per_cell branch, one dataset per system, band, and code:

from canvod.store import AnalysisStorage

storage = AnalysisStorage("/path/to/vod_store")
storage.store_percell_timeseries(percell_ds, system="G", band="L1", code="C")
storage.list_percell_datasets()  # ['C_B2b_I', 'E_E1_C', 'G_L1_C', ...]
ds = storage.load_percell_timeseries(system="G", band="L1", code="C")
